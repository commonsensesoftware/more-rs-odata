# Static CSDL conformance audit

The implementation is **not fully CSDL-conformant**. This audit separates delivered
features from proof of conformance and records the remaining static obligations.
Completion of the original seven delivery tasks does not certify every normative
clause or every XML/JSON representation of it.

## Sources and method

- [CSDL XML 4.01 OS](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/os/odata-csdl-xml-v4.01-os.html)
- [CSDL JSON 4.01 OS](https://docs.oasis-open.org/odata/odata-csdl-json/v4.01/os/odata-csdl-json-v4.01-os.html)
- [XML schemas](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/os/schemas/)
- [JSON schema](https://docs.oasis-open.org/odata/odata-csdl-json/v4.01/os/schemas/)
- [OData 4.01 ABNF and test cases](https://docs.oasis-open.org/odata/odata/v4.01/os/abnf/)

[conformance-requirements.json](conformance-requirements.json) inventories 485
normative **paragraphs**, 257 XML and 228 JSON. A paragraph can contain multiple
MUST/MUST NOT/SHOULD obligations. Each has a stable edition/section/paragraph ID,
source anchor, full requirement text, and requirement keywords. Example text and
terminology paragraphs are retained and explicitly classified, rather than
silently removed. The inventory is regenerated by
[inventory-conformance.ps1](../scripts/inventory-conformance.ps1).

[conformance-matrix.json](conformance-matrix.json) is the requirement-to-code-to-test
mapping. Match each paragraph's section to the longest section prefix, then apply
an exact-ID override if present. Every paragraph has a disposition. Test entries
are either a focused test function or a suite; a suite link is related evidence,
not a claim that it proves each sentence in the paragraph. The audit test checks
inventory completeness, unique IDs, override integrity, and real code/test links.

| Disposition | Paragraphs | Meaning |
|---|---:|---|
| covered | 18 | Direct evidence for the complete paragraph identified here |
| partial | 402 | Implementation exists, but behavior or independent clause-level evidence is incomplete |
| unsupported | 6 | Known static obligation not completely implemented |
| advisory | 26 | SHOULD guidance that does not reject documents |
| outside-static-scope | 33 | HTTP, runtime values/execution, metarules, or example text |

These counts are **not a conformance percentage**. The conservative partial status
also covers implemented rules that lack independent positive and negative cases
in both representations. Mixed static/runtime paragraphs stay partial, with their
static code and runtime responsibility explained in the notes.

## What prevents a full validation claim

The follow-up items below are in dependency order. Each item links to exact
requirement IDs through the matrix; permissions expressed with MAY, format
defaults, and referenced grammar artifacts also matter even when not represented
by a capitalized MUST paragraph.

1. [Source fidelity and strict representation parity](../TODO/conformance-source-parity.md):
   implemented strict JSON alias-only qualification, same-container binding target
   spelling, declaration member checks, and authored versus defaulted collection
   nullability. Meaningful order is retained; serialization groups cross-kind
   interleaving as documented in the delivery record. Expression-specific and
   cross-format output checks remain in the following tasks.
2. [Reference annotations and complete scope isolation](../TODO/conformance-reference-metadata.md):
   implemented reference/Include metadata, schema-version loader hints, and scope
   checks for structural paths and expression bindings, including dependencies
   loaded transitively. Additional path syntax is the next task.
3. [Complete annotation path grammar](../TODO/conformance-expression-paths.md):
   key predicates, ordered indexes, `$count`, empty paths, collection traversal
   limits, implicit media terms, and all target-relative starting contexts.
4. [Complete recursive expression semantics](../TODO/conformance-expression-semantics.md):
   the full canonical function signature catalog and numeric promotion,
   base-term record member completion, numeric enum values, URL result typing,
   and literal/label edge cases. Unknown bindings are currently diagnostics,
   which is useful but does not establish support for every valid expression.
5. [Lossless and configurable format output](../TODO/conformance-output-options.md):
   IEEE754Compatible, arbitrary precision decimals, metadata modes, nested typed
   literal conversion, reference URI rebasing, and full semantic round-trip
   equivalence. Guarded output checks grammar/version before writing; it does not
   substitute for validation of a graph resolved with the caller's loader.
6. [Tolerant recovery and exhaustive evidence](../TODO/conformance-consumer-evidence.md):
   preserving or ignoring unavailable annotation constructs without rejecting a
   well-formed document, and a complete clause-level paired-format fixture corpus.

## Profiles and recommendations

Strict source parsing runs before normalization; semantic strict reports include
annotation diagnostics. Tolerant semantic reports exclude annotation diagnostics
from validity. Legacy parsing/output APIs retain their compatibility behavior.
The distinction does not yet solve recovery from every malformed or future
annotation expression at the parser boundary.

Case-only identifier collisions, future AppliesTo values, absent navigation
bindings, 4.0 collection nullability, and compact JSON default omission are
advisory. No separate warning stream is implemented yet. Reference filtering
SHOULD rules are implemented and tested. Choosing queryable service-document
entries and fetching a requested schema version belong to caller policy; the
missing reference metadata still prevents conveying the latter policy completely.

Runtime expression evaluation, service-data key uniqueness, referential integrity,
delete execution, function side effects, HTTP negotiation, and validating actual
remote URL-reference response bodies are outside static validation. Parameter
order compatibility across service revisions also needs a prior model.

## Grammar artifact coverage

The XSD declaration/expression families were compared with parser owner/attribute
tables, arity checks, and the syntactic model. The audit found and fixed empty XML
containers/enumerations and attribute entity decoding. Existing tests exercise
document cardinalities, namespace boundaries, expression arity, and new operators.
Reference annotations, complete source interleaving, and tolerant extension
recovery remain explicit gaps.

The JSON prose adds alias-only spelling and media-type output requirements beyond
the normalized EDM. Both are recorded above. The JSON schema is complementary;
it does not prove reference resolution, inheritance, or expression assignability.

ABNF identifier/qualified-name rules map to `conformance.rs`, scalar lexical
families to `validator/values.rs`, and CSDL expression paths to the resolver.
The complete referenced ABNF test corpus and every JSON-schema branch have **not**
been imported as executable tests. That evidence gap is tracked rather than
counted as covered. Unicode identifier tests alone do not prove path/literal ABNF.

## Regression evidence added by the audit

`conformance_audit.rs` checks XML attribute escaping and cardinalities, positive
and negative two-operand If contexts in both formats, matrix integrity, and a
known unsupported `$count` path. The last test deliberately asserts an explicit
diagnostic, not conformance of that path. Replace it with a positive semantic
test when the path task is implemented. Existing suites supply referenced-document
cycles/scopes/filtering and semantic/format round trips.
